# 测试用例设计方法详解

本文档为 test-design skill 在 Step 2（测试场景分析）时的方法参考。按 SKILL.md 的子流程顺序执行：先做第 0 节测试因子分析（必做），再按方法路由表选用第 1-8 节方法，最后用第 9 节输出域分析做覆盖校验。

## 0. 测试因子分析（每个功能点必做的前置分析）

测试场景遗漏的根源通常是「分析维度不全」而非「方法不会用」。在选用任何设计方法之前，先对每个功能点系统枚举测试因子，保证维度不漏，再由因子组合生成场景。

**操作步骤**：

1. 按五个维度枚举因子：
   - **输入因子**：每个输入参数（含隐藏参数、有默认值的可选参数）的类型、范围、格式、长度、必填性——**每个参数至少一个因子**，遗漏参数即遗漏场景
   - **状态因子**：功能点依赖或改变的对象状态（前置状态 × 后置状态）、全局状态、会话状态
   - **时序因子**：操作顺序（先 A 后 B / 先 B 后 A）、调用次数（首次 / 重复）、调用间隔（连续 / 延迟后）、并发（同时 / 交错）
   - **数据因子**：数据规模（空 / 单条 / 多条 / 上限）、数据内容（典型值 / 边界值 / 特殊字符 / 多字节编码）、数据分布（有序 / 逆序 / 重复 / 随机）
   - **环境因子**：功能测试范围内的环境前提（资源可用 / 不可用、依赖服务正常 / 异常、配置项不同取值）
2. 为每个因子列出取值水平（水平即等价类代表值，与第 1 节衔接）。
3. 完整性三必查：
   - 功能点的**每个输入参数**都出现在因子表中
   - 功能点涉及的**每个可达状态**都出现在状态因子中
   - 功能点的**每个输出（含每个错误码/提示）**都能被某个因子组合触发（用第 9 节输出域分析校验）
4. 因子表是场景生成的直接素材：单因子变化生成基本场景；多因子组合按判定表（规则类）、成对组合（参数类）、场景法（时序类）生成组合场景。

**示例**：修改密码功能 → 输入因子：旧密码（对/错/空）、新密码（格式合法/非法/与旧密码相同/边界长度）；状态因子：已登录/会话过期；时序因子：连续修改两次/修改后立即用旧密码登录；数据因子：密码含特殊字符/含中文；环境因子：依赖的认证服务正常/异常。

## 1. 等价类划分

将输入域划分为若干等价类，每类选取代表值，用少量输入代表大量取值。

**操作步骤**：
1. 从因子表的输入因子中取每个输入项及其约束。
2. 划分有效等价类（符合规则，用于正常场景）和无效等价类（违反规则的每一种方式各为一类，用于异常场景）。
3. 为每个等价类设计一个代表值。
4. 有效类可合并覆盖（一条用例覆盖多个有效类），无效类必须逐类单独覆盖（一条用例只违反一条规则）。

**示例**：手机号要求 11 位纯数字 → 有效类：11 位数字；无效类：非数字、长度≠11、空值、含空格。

## 2. 边界值分析

缺陷常集中在输入/输出的边界及邻域，在等价类边界取值补充场景。

**操作步骤**：
1. 找到每个输入项的边界（上边界 B_max、下边界 B_min）。
2. 取 5 个点：B_min-1、B_min、正常值、B_max、B_max+1。
3. 对每个边界点判定预期结果（文档定义了接受/拒绝行为）。

**示例**：用户名 6-20 字符 → 取 5、6、10、20、21 字符各一条用例。

## 3. 判定表法

适用于多个条件的组合决定不同结果的业务规则。

**操作步骤**：
1. 列出所有条件（每个条件取真/假，多值条件拆为多列）。
2. 列出所有动作（结果分支）。
3. 枚举条件组合，合并不可能或结果相同的组合。
4. 每一列（一条规则）生成至少一个测试场景。

**示例**：优惠券规则「会员且订单满 100 元打 8 折；会员但不满 100 元打 95 折；非会员无折扣」→ 3 列判定表 → 3 个场景。

## 4. 因果图法

条件之间存在约束（互斥、包含、要求、屏蔽）时，先画因果图再转换为判定表。当判定表条件可以独立取值、无约束时，直接用判定表法即可，不必画因果图。

## 5. 场景法

适用于跨多个步骤的业务流程（如下单、审批、支付）。

**操作步骤**：
1. 从文档中识别基本流：一切顺利时的主路径。
2. 识别备选流：每个可能偏离基本流的分支（校验失败、数据缺失、用户取消、流程中断后恢复等）。
3. 组合基本流与备选流生成场景：主场景 = 纯基本流；每个备选流至少生成一个场景（基本流 + 该备选流）。
4. 每个场景标注触发备选流的具体条件。

**示例**：下单流程基本流：选商品→确认订单→支付→出库。备选流：库存不足、支付超时、支付失败后重试 → 各生成一个场景。

## 6. 状态迁移法

适用于有状态的对象（订单、工单、账号等）。

**操作步骤**：
1. 从文档提取所有状态与触发迁移的事件，画出状态迁移图。
2. 覆盖每一条合法迁移边（状态 A --事件--> 状态 B）。
3. 对关键状态设计非法迁移尝试（在当前状态下触发不该接受的事件，预期被拒绝——若规格未定义拒绝行为，按合理假设处理并登记假设）。
4. 考虑迁移过程中的并发/重复触发（重复点击、事件重发）。

## 7. 组合覆盖法（成对组合 + 正交实验）

多参数功能的组合覆盖分两档：**成对组合（pairwise）是默认最低要求，正交表用于进一步精简**。

**第一档：成对组合（所有含 ≥2 个输入因子的功能点默认必做）**

任意两个参数（因子）的所有取值对至少出现一次。两两组合缺陷检出率在工程上已接近全组合。

1. 从因子表取各输入因子及其水平。
2. 构造组合表：先覆盖高风险取值对（含无效值的对优先），再补齐剩余取值对。
3. 每个无效取值至少与一个正常取值组合过一次（无效值单独触发的场景由等价类覆盖）。

**第二档：正交实验（成对组合后数量仍然爆炸时）**

1. 选择列数≥因素数、水平数匹配的最小正交表（如 L9(3^4)）。
2. 按表生成组合场景，另补「全部参数取最优值」和「全部参数取最差值」两条组合。

**示例**：三个参数 A(3 水平)、B(2 水平)、C(2 水平)，全组合 12 条 → 成对组合可压缩到约 6 条。

## 8. 错误推测法

凭经验列举易错点补充场景。必须对照 `abnormal-checklist.md` 的通用清单逐项检查，不依赖灵感。此方法是对前七种方法的兜底补充，不作为主要方法。

## 9. 输出域分析法（覆盖校验，必做）

从输出侧反向验证覆盖完整性：**任何未被场景触发的输出（尤其是错误码）就是覆盖缺口**。

**操作步骤**：

1. 从规格与 demo 收集功能点的全部输出：返回值、成功输出、每个错误码、每条提示文案、可见副作用（数据变更、状态变化、通知发送）。
2. 为每个输出反推触发条件（输入因子组合或状态/时序条件）。
3. 对照场景矩阵逐一核对：无场景触发的输出 → 反推触发条件补设计场景；确实无法触发的输出（防御性代码）→ 登记到「假设登记」并说明判断依据。

**示例**：登录功能输出有「成功」「密码错误」「账号不存在」「账号锁定」四种，场景矩阵只覆盖了前三种 → 「账号锁定」缺触发场景（连续 N 次失败），必须补。

## 场景编号与记录规范

- 场景编号：TS-001 起连续编号。
- 每个场景必须记录：编号、来源功能点（FP-xx）、描述、类型（正常/异常）、BUG 类别、设计方法、预期结果。
- 场景的来源因子应可从因子表追溯：场景描述中体现关键因子的取值。
- 预期结果必须来自规格或 demo 的明确定义；两者均未定义时按合理假设给出并标注「基于假设」，在测试设计文档「假设登记」章节中登记。
