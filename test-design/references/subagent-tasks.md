# 子 agent 委派任务清单与输出契约

## 分工总原则

**主 agent 专注测试场景分析**：规格拆解、需求项编号、功能点提取、因子分析、场景设计、组合分析、BUG 专项、输出域校验、穷尽性审计、用例设计、设计文档编写。这些是决定交付质量的核心工作，不得被环境类事务打断。

**子 agent 承担一切与场景分析无关的环境与工具性工作**：构建/编译方式确认、测试框架与运行入口识别、demo 格式约定提取、环境依赖确认、探针行为验证、运行结果解析方式确认，以及执行期的编译/运行报错排查。

**主 agent 只接收结论**：子 agent 返回结构化结论与可直接使用的小产物（命令、骨架代码、约定清单）；**不返回过程日志、编译报错堆栈、试错轮次、文件全文**。

**派发规则**：相互独立的任务并行派发多个子 agent，不串行等待；同一任务内的多轮尝试由子 agent 内部消化；任务边界清晰（一个问题一个任务），避免"什么都查一下"的宽泛委派。

**回退**：环境不支持子 agent 时，主 agent 自行完成，但同样只把结论带出，过程产物不进交付物与主推理链。

## 统一输出契约

每个子 agent 任务按同一模板返回，控制在最小必要信息量：

```
任务编号：T-x
结论：{一句话可直接使用的结论}
证据摘要：{一行，如「cmake --version 输出 3.28」「demo 用例使用 ASSERT_EQ 宏」}
可用产物：{命令序列 / 代码骨架 / 约定清单，按需，尽量短}
不确定项：{未能确认的问题及原因；无则写「无」}
```

禁止返回：完整日志、报错堆栈、文件全文、逐步操作叙述。

## 任务类型清单

### T1 构建与编译方式确认

- **输入**：项目根路径。
- **执行**：确认构建系统与工具链、生成器、构建目录、目标、可执行文件名与输出路径；实际执行一次完整构建验证命令可用。
- **返回**：可直接执行的编译命令序列 + 可执行文件路径 + 构建耗时量级。
- **用途**：Step 7 直接使用，免去主 agent 试探。

### T2 测试框架与被测接口识别

- **输入**：项目根路径、testcase/ 目录。
- **执行**：识别测试框架与断言宏、用例函数签名与命名约定、用例注册机制、runner/main 结构、运行命令、输出格式与通过/失败判定方式；同时识别**被测系统对外暴露的接口**（可用头文件、函数签名、调用方式），供探针（T5）与用例编写使用。**注意：目标系统为黑盒，不含实现源码，只能确认接口形态而非实现细节。**
- **返回**：一份「用例编写与运行约定」清单 + 一段可直接复制的最小用例骨架代码 + 运行命令 + 被测接口签名摘要。
- **用途**：Step 6 编码、Step 7 运行、T5 探针直接依据。

### T3 demo 与既有用例格式提取

- **输入**：testcase/ 目录下的 demo 与既有 testcase.c。
- **执行**：提取既有用例的组织方式（前置/操作/断言/清理如何编排）、命名风格、数据构造方式。
- **返回**：格式约定条目清单（不超过 10 条）。
- **用途**：Step 6 保证新增用例与既有风格一致。

### T4 环境依赖确认

- **输入**：项目根路径。
- **执行**：确认编译与运行所需工具是否存在及版本（编译器、构建工具、运行库）。
- **返回**：工具清单与版本 + 缺失项（若有）。
- **用途**：提前暴露环境阻塞，避免执行到 Step 7 才发现。

### T5 黑盒行为验证（Step 0「黑盒行为验证规则」使用）

- **输入**：待验证问题清单（PQ-xx | 行为假设 | 影响的 REQ/功能点）。
- **执行**：目标系统是黑盒（无源码），探针通过其对外暴露的接口（接口形态由 T1/T2 确认）调用被测功能；在 `testcase/` 之外的临时位置编写、编译、运行，逐条验证；用后清理探针文件与临时构建产物。
- **返回**：逐条结论表 `问题编号 | 观察到的行为 | 结论 | 证据摘要`。
- **约束**：观察结果只用于校准理解；预期结果仍须能从规格或 demo 推导。

### T6 运行结果判定方式确认

- **输入**：项目的测试运行命令与样例输出。
- **执行**：确认如何从运行输出判定用例通过/失败/崩溃、失败信息呈现方式、退出码含义。
- **返回**：判定规则说明 + 一段样例输出的解读。
- **用途**：Step 7 结果处理依据。

### T7 编译/运行报错排查（执行期按需）

- **输入**：失败现象（如「编译报错」「运行中断」）+ 涉及的源文件范围。
- **执行**：定位根因，判断是否由新增用例代码引起。
- **返回**：根因一句话 + 涉及的文件与位置 + 修复方案 + 是否为新增代码问题（是/否）。
- **约束**：子 agent 只诊断与提出方案；**修改 testcase.c 由主 agent 执行**（保持设计文档与代码的一致性由主 agent 掌握）。

## 使用方式

- Step 0 启动时，将 T1-T4 作为一批并行派发（互不依赖），一次性拿到环境与格式结论；同时整理待验证问题清单并派发 T5。
- Step 6/7 直接使用 T1、T2、T6 的结论，不再重新试探。
- 执行期遇到编译/运行异常，派发 T7，按返回的根因与方案由主 agent 实施修复。
