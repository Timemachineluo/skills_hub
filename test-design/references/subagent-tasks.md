# 子 agent 委派任务清单与输出契约

职责划分见 SKILL.md 核心原则 8；本文档提供可执行的任务清单、输出契约与派发方式。

**派发规则**：任务边界清晰（一个问题一个任务），避免「什么都查一下」的宽泛委派；同一任务内的多轮尝试由子 agent 内部消化。

**并发上限（硬性）**：**任何时刻最多并行 2 个子 agent**；当前批任务全部返回后再按需派发新任务，禁止一次性铺开全部任务。需要多个任务时按依赖关系分批，互不依赖的优先同批（每批 ≤2）。

**回退**：环境不支持子 agent 时，主 agent 自行完成，但同样只把结论带出，过程产物不进交付物与主推理链。

## 统一输出契约

每个子 agent 任务按同一模板返回，控制在最小必要信息量：

```
任务编号：T-x
结论：{一句话可直接使用的结论}
证据摘要：{一行，如「cmake --version 输出 3.28」「demo 用例使用 ASSERT_EQ 宏」}
可用产物：{命令序列 / 代码骨架 / 约定清单，按需，尽量短}
不确定项：{未能确认的问题及原因；无则写「无」}
```

禁止返回：完整日志、报错堆栈、文件全文、逐步操作叙述。

## 任务类型清单

### T1 构建与编译方式确认

- **输入**：项目根路径。
- **执行**：确认构建系统与工具链、生成器、构建目录、目标、可执行文件名与输出路径；实际执行一次完整构建验证命令可用。
- **返回**：可直接执行的编译命令序列 + 可执行文件路径 + 构建耗时量级。
- **用途**：Step 7 直接使用，免去主 agent 试探。

### T2 测试框架与被测接口识别

- **输入**：项目根路径、testcase/ 目录。
- **执行**：识别测试框架与断言宏、用例函数签名与命名约定、用例注册机制、runner/main 结构、运行命令、输出格式与通过/失败判定方式；同时识别**被测系统对外暴露的接口**（可用头文件、函数签名、调用方式），供探针（T5）与用例编写使用。**注意：目标系统为黑盒，不含实现源码，只能确认接口形态而非实现细节。**
- **返回**：一份「用例编写与运行约定」清单 + 一段可直接复制的最小用例骨架代码 + 运行命令 + 被测接口签名摘要。
- **用途**：Step 6 编码、Step 7 运行、T5 探针直接依据。

### T3 demo 与既有用例格式提取

- **输入**：testcase/ 目录下的 demo 与既有 testcase.c。
- **执行**：提取既有用例的组织方式（前置/操作/断言/清理如何编排）、命名风格、数据构造方式。
- **返回**：格式约定条目清单（不超过 10 条）。
- **用途**：Step 6 保证新增用例与既有风格一致。

### T4 环境依赖确认

- **输入**：项目根路径。
- **执行**：确认编译与运行所需工具是否存在及版本（编译器、构建工具、运行库）。
- **返回**：工具清单与版本 + 缺失项（若有）。
- **用途**：提前暴露环境阻塞，避免执行到 Step 7 才发现。

### T5 黑盒行为验证（Step 0「黑盒行为验证规则」使用）

- **输入**：待验证问题清单（PQ-xx | 行为假设 | 影响的 REQ/功能点）。
- **执行**：目标系统是黑盒（无源码），探针通过其对外暴露的接口（接口形态由 T1/T2 确认）调用被测功能；在 `testcase/` 之外的临时位置编写、编译、运行，逐条验证；用后清理探针文件与临时构建产物。
- **返回**：逐条结论表 `问题编号 | 观察到的行为 | 结论 | 证据摘要`。
- **约束**：观察结果只用于校准理解；预期结果仍须能从规格或 demo 推导。

### T6 运行结果判定方式确认

- **输入**：项目的测试运行命令与样例输出。
- **执行**：确认如何从运行输出判定用例通过/失败/崩溃、失败信息呈现方式、退出码含义。
- **返回**：判定规则说明 + 一段样例输出的解读。
- **用途**：Step 7 结果处理依据。

### T7 编译/运行报错排查（执行期按需）

- **输入**：失败现象（如「编译报错」「运行中断」）+ 涉及的源文件范围。
- **执行**：定位根因，判断是否由新增用例代码引起。
- **返回**：根因一句话 + 涉及的文件与位置 + 修复方案 + 是否为新增代码问题（是/否）。
- **约束**：子 agent 只诊断与提出方案；**修改 testcase.c 由主 agent 执行**（保持设计文档与代码的一致性由主 agent 掌握）。

### T8 跨功能点组合场景分析（专职子 agent，子流程 2b）

**这是唯一承担"场景生成"职能的委派任务**，其余任务均为环境/确认类。子 agent 只专注多功能点叠加的场景分析，主 agent 负责提供输入与整合结果。

- **输入（由主 agent 准备并完整传递）**：
  1. 功能设计规格（或其相关章节）；
  2. 需求项清单（REQ-xx → 功能点映射）；
  3. 功能点清单：编号、名称、角色（状态变更型/状态读取型/数据依赖型）、输入、处理规则、输出/预期行为、前置条件；
  4. 各功能点的因子表（五维因子与取值水平）；
  5. 数量下限与输出格式要求（见下）。
- **执行**：按 design-methods.md 第 10 节——识别功能角色与依赖 → 构建全局状态机 → 三层发散生成（① 两步序列矩阵穷举，适用格全部生成含 A→A；② 六种模式多步旅程，每对象每模式 ≥1 条并做变体扩展；③ 组合 × 因子交叉）→ 自检数量下限 → 输出场景表。
- **返回**：组合场景清单 + 统计，**不返回分析过程叙述**：

```
组合场景清单（逐条）：
  功能点序列 | 组合模式 | 场景描述 | 类型（正常/异常）| BUG 类别 | 预期结果 | 推导依据（REQ/规格出处）
统计：
  两步序列矩阵：义务格数 X，已覆盖 Y，不适用 Z（附不适用原因清单）
  六模式：每个有状态交互对象 × 6 的覆盖情况
  组合场景总数：N（相对单功能点场景数的比例）
  实际使用的数量下限规则：{下限值} / 不满足项：{列表，无则写「无」}
不确定项：{规格未定义、需主 agent 判定的事项}
```

- **约束**：只做组合场景分析，不重复生成单功能点场景；每条预期结果必须能从规格或 demo 推导（黑盒观察不得作为唯一依据）；数量下限不达标时**由该子 agent 继续补足后再返回**，不得把缺口留给主 agent。

### T9 四类 BUG 专项场景分析（专职子 agent，子流程 2c）

与 T8 并列的第二个专职生成任务。**分析粒度是本任务的核心**：以「风险对象」而非「功能点」为分析单元——按功能点生成必然遗漏，按风险对象逐个构造才够细。

- **输入（由主 agent 准备并完整传递）**：
  1. 功能设计规格（或其相关章节）；
  2. 需求项清单（REQ-xx → 功能点映射）；
  3. 功能点清单：编号、名称、接口形态（函数签名与参数）、输入约束、处理规则、输出/错误码、前置条件；
  4. 各功能点的因子表（五维因子与取值水平）；
  5. `bug-category-checklists.md` 清单全文；
  6. 数量下限与输出格式要求。
- **执行（精细粒度，两步走）**：
  1. **枚举风险对象**：对每个功能点逐一列出下列对象——输入缓冲区及其长度上限、字符串与终止符、索引与数组下标、循环及其迭代次数、算术运算与类型转换、状态字段及其生命周期、返回值/错误码分支、资源分配与释放点、外部依赖调用点。
  2. **按对象逐个套清单**：对每个风险对象套用安全/可靠性/性能清单中的适用项生成专项场景；**同一清单项作用于不同风险对象时必须分别生成**（如缓冲区 A 与缓冲区 B 的边界场景是两条），不得合并。
- **返回**：

```
风险对象清单（每个功能点）：对象类型 | 位置/名称 | 关联风险类别
专项场景清单（逐条）：功能点 | 风险对象 | 触发手法 | 精确触发值 | BUG 类别 | 预期结果 | 推导依据
统计：
  每个功能点每类场景数；四类清单适用项覆盖率；未覆盖项及原因
  风险对象覆盖：识别对象数 X，已生成场景 Y，缺口列表（无则写「无」）
不确定项：{规格未定义、需主 agent 判定的事项}
```

- **数量下限（不达标自行补足后再返回）**：每个识别出的风险对象不少于 1 条专项场景；每个功能点的安全/可靠性/性能三类清单适用项均有对应场景或标注不适用及原因。
- **约束**：测试数据必须是精确触发值（如「size-1 / size / size+1」「INT_MAX」「循环 1000 次」），禁止「超长输入」类模糊描述；只做专项场景，不重复功能异常场景与组合场景；预期结果须能由规格或 demo 推导。

## 使用方式

- **Step 0**：分批派发 T1-T4（每批最多 2 个，完成后再派下一批），拿到环境与格式结论；整理待验证问题清单后派发 T5。
- **Step 2 子流程 2b**：功能点清单与因子表就绪后，派发 T8；主 agent 整合返回的组合场景表，统一编号、与单功能点场景查重、核对数量下限与推导依据；有缺口时带具体缺口再次派发 T8 补充。
- **Step 2 子流程 2c**：派发 T9 做四类 BUG 专项分析（可与 T8 同批，但注意并发上限）；主 agent 整合时重点核对「每个风险对象 ≥1 条」与精确触发值，缺口带清单再次派发 T9。
- **Step 6/7**：直接使用 T1、T2、T6 的结论，不再重新试探；执行期遇到编译/运行异常派发 T7，按返回根因与方案由主 agent 实施修复。
- **全程**：并发派发不得超过 2 个子 agent。
