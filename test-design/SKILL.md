# Test Design（测试设计）

## Overview

此 skill 用于在**无人干预**条件下，将功能设计规格与测试样例 demo（位于项目 `testcase/` 路径下）自动转化为完整测试设计与测试用例代码，并以**发现 BUG**（而非仅验证功能正确）为导向：测试场景覆盖功能（正常/异常）以及安全、可靠性、性能三类 BUG 专项。核心做法：先把规格逐条编号拆解为需求项，再映射为可追溯的功能点清单，对每个功能点按确定性规则选用用例设计方法生成正常/异常测试场景，并逐功能点套用四类 BUG 专项清单生成对抗性场景，经覆盖率自检关卡后展开为详细用例，**先生成测试设计文档（作为编写用例的直接参照物），再依据该文档将新增测试用例按 demo 格式以 C 代码写入 `testcase/testcase.c`**。

**运行模式：全程自动，禁止中途向用户提问或等待确认。** 所有不确定信息由模型按「合理假设原则」自行处理并登记。

## 核心原则（防跑偏、防遗漏，全程必须遵守）

1. **只基于输入材料，禁止臆造需求**：所有测试场景必须来源于功能设计规格或 demo 的明确信息。规格未定义的行为，按合理假设设计并登记到「假设登记」章节，同时在场景中标注「基于假设」。
2. **BUG 发现导向的对抗性思维**：测试的目的不是证明功能正确，而是主动构造能暴露 BUG 的条件。功能场景（以需求为出发点）之外，每个功能点必须再从安全、可靠性、性能三个视角审查一遍（见 references/bug-category-checklists.md），安全类按「不应崩溃/不应越界」、可靠性类按「应报错而非崩溃」、性能类按「应在合理时间内返回」作为基线预期。
3. **宁多勿漏**：无法判断某项是否需要覆盖时，一律设计场景并标注。漏分析是本任务最大风险，多余场景的成本远低于遗漏场景的损失。
4. **每一步有中间产物，先设计后编码**：工作流分七个阶段，每阶段必须产出确定的中间产物（需求项清单 → 功能点清单 → 场景矩阵 → 用例表 → 测试设计文档 → testcase.c 用例代码），测试设计文档必须先于用例代码完成并作为编码的唯一参照。禁止跳过中间产物直接写代码或文档。
5. **全程可追溯**：需求项（REQ-xx）→ 功能点（FP-xx）→ 场景（TS-xxx）→ 用例（TC-xxx）四级编号逐级映射，最终文档必须包含两级追溯矩阵，任何一级出现无来源或无覆盖的条目均视为分析遗漏。
6. **确定性方法路由**：按「方法路由表」为每个功能点选择设计方法，不得凭感觉自由发挥；所有功能点必须用异常场景清单（见 references/abnormal-checklist.md）和四类 BUG 专项清单兜底补充。
7. **关卡不通过则返工**：覆盖率自检关卡（Step 4）中的检查项必须逐条核对，任何一条不满足必须返回上一步补充，禁止带缺口输出。

## Workflow

### Step 0：输入材料解析

**材料 1：功能设计规格**

逐段逐条通读，为每条可验证的陈述分配需求项编号（REQ-01、REQ-02…）。需求项包括但不限于：

- 明确的功能描述（动词句）
- 输入约束（类型、范围、格式、必填性）
- 输出与提示文案（每个错误提示即一条需求项）
- 业务规则、逻辑分支、计算公式
- 状态定义与流转
- 权限与角色规则
- **隐性需求**：规格中一笔带过但可验证的内容（如"默认值为 X""页面显示 Y"）

**材料 2：测试样例 demo（位于项目 `testcase/` 路径下）**

读取项目 `testcase/` 目录下的样例文件（demo 及既有的 testcase.c），解析 demo 的三重价值：

1. **格式规范**：提取用例的编写约定——测试框架与断言方式（如 assert/CuTest/Check）、测试函数结构与命名、注册/运行方式（main 或 runner）、头文件引用、代码风格，最终写入 `testcase/testcase.c` 的新增用例必须严格遵循该格式。
2. **隐含行为**：demo 中体现但规格未写明的行为（边界处理、异常提示、默认逻辑），作为隐含需求项补充进需求项清单，来源标注「demo 推断」。
3. **理解校准**：将 demo 样例代入自己的理解中验证，若与 demo 实际表现矛盾，说明理解有偏差，必须回头修正需求项清单。

若项目 `testcase/` 路径下不存在 demo，按规格继续，用例按标准 C 断言风格编写并登记假设。

### Step 1：功能点提取（两遍扫描，防漏关键步骤）

**第一遍：正向提取**。将需求项归组为功能点，每个功能点包含：

| 字段 | 说明 |
|------|------|
| 编号 | FP-01、FP-02…（全文档唯一） |
| 功能点名称 | 动宾结构，如「提交订单」「校验手机号格式」 |
| 来源需求项 | REQ-xx 列表（至少 1 条，可多条归组） |
| 输入 | 输入项、类型、取值范围/格式约束 |
| 处理规则 | 规格/demo 中明确的业务规则、逻辑分支 |
| 输出/预期行为 | 成功与失败时的表现 |
| 前置条件 | 触发该功能点所需状态、权限、数据 |
| 特征标签 | 【输入域】【规则组合】【流程】【状态流转】【交互界面】等，用于 Step 2 方法路由 |

**第二遍：反向查漏（必须执行，不可跳过）**。重新通读规格全文，按以下维度逐项检查是否已全部纳入功能点清单：

- 每个输入字段 / 界面控件 / 接口参数
- 每个输出结果 / 每条提示文案
- 每条业务规则的每个分支
- 每个状态及其所有出入迁移
- 每种角色 / 权限组合
- 每个异常处理描述
- demo 中出现但规格正文未提及的行为

发现遗漏立即补入功能点清单。完成后输出「需求项对照表」（REQ → FP 映射），**任何 REQ 未被 FP 覆盖即视为分析遗漏，必须处理（归组或单独建 FP）后方可继续**。

### Step 2：测试场景分析（功能场景 + 四类 BUG 专项场景）

对每个功能点，按方法路由表选择设计方法，产出「测试场景矩阵」。方法详见 `references/design-methods.md`。

**方法路由表（确定性规则）**：

| 功能点特征 | 必选方法 |
|------------|----------|
| 有输入域（数值、文本长度、格式、日期等） | 等价类划分 + 边界值分析 |
| 存在多条件组合决定结果的规则 | 判定表法（条件多且有约束时用因果图辅助） |
| 涉及跨步骤业务流程 | 场景法（基本流 + 备选流） |
| 对象有状态流转（如订单状态） | 状态迁移法（覆盖所有迁移边） |
| 多参数组合且组合爆炸 | 正交实验法 |
| 所有功能点（兜底） | 错误推测法，对照 `references/abnormal-checklist.md` 逐项检查 |
| 所有功能点（BUG 专项，必做） | 对照 `references/bug-category-checklists.md` 逐项检查 |

**子流程 2a：功能场景**。按方法路由表前六行生成正常/异常功能场景。

**子流程 2b：四类 BUG 专项场景（必做，不可跳过）**。对每个功能点，依次套用 `references/bug-category-checklists.md` 的安全、可靠性、性能三节清单，适用项各生成专项场景；功能类清单用于查漏补缺功能场景。要点：

- 专项场景以「怎么让它出错」为出发点：安全类构造溢出/越界/注入的精确攻击值，可靠性类构造崩溃输入与资源泄漏时序，性能类构造最大规模与最坏情况输入。
- 有缓冲区/字符串处理的功能点，安全类场景至少覆盖缓冲区边界精确值（长度-1/长度/长度+1）。
- 有循环/查找/排序的功能点，性能类场景至少覆盖最大规模输入与最坏情况构造。
- 专项场景的测试数据必须给出精确触发值（如「256 字节输入」「INT_MAX」「循环 1000 次」），不得写「超长输入」等模糊描述。

场景矩阵中每个场景必须包含：场景编号（TS-xxx）、对应功能点编号、场景描述、类型（正常/异常）、**BUG 类别（功能/安全/可靠性/性能）**、使用的设计方法、预期结果（须来自规格或 demo；两者均未定义的按合理假设或核心原则 2 的 BUG 基线预期给出，并标注「基于假设」）。

正常场景与异常场景用类型列区分。异常场景数量不得少于正常场景的 50%（若低于，说明异常分析不足，回到路由表补做）。四类 BUG 类别各自至少有 1 个专项场景属于 P1 及以上优先级。

### Step 3：用例展开

将每个测试场景展开为 1 条或多条可执行测试用例：

- **用例编号**：TC-xxx（与场景编号 TS-xxx 对应，可追溯）
- **用例标题**：一句话描述（动宾结构）
- **优先级**：P0（主流程正常场景）/ P1（重要分支与高频异常）/ P2（低概率异常与边界组合）
- **前置条件**：状态、数据、权限准备
- **测试数据**：具体到值（含边界值具体取值），不得写「任意合法值」
- **操作步骤**：编号步骤，单步骤单一操作
- **清理步骤**：用例执行后恢复到执行前状态的资源清理操作（见下方清理规则）
- **预期结果**：具体可判定，对应功能点的输出定义；demo 有格式约定的按 demo 格式表述

**清理步骤规则（每条用例必填）**：

1. 凡用例产生了持久化变更（新增/修改/删除了数据、成员、记录、文件、状态），必须设计对应清理步骤将其恢复（如「删除本用例新增的成员 xxx」），避免污染后续用例。
2. 确无资源变更的只读用例，清理步骤填「无需清理」，不得留空。
3. 清理步骤必须**幂等**：目标资源已不存在时清理不报错、不影响用例判定。
4. 预期结果的验证数据在清理前采集完毕，清理不参与断言。

规则：一个场景含多组测试数据时拆为多条用例；预期结果含多个验证点时逐条列出。本阶段产物是用例表（设计层），C 代码在 Step 6 依据测试设计文档编写。

### Step 4：覆盖率自检（硬性关卡，替代人工评审）

逐条核对以下清单，任何一条不满足即返回对应步骤补充，全部满足才能输出：

- [ ] 每条需求项（REQ-xx）已映射到功能点，需求项对照表无空缺
- [ ] 每个功能点至少有 1 个正常场景
- [ ] 每个有输入约束的字段至少有 1 个无效等价类场景
- [ ] 每条业务规则的每个分支（含判定表每一列）至少被 1 个场景覆盖
- [ ] 有状态流转的功能点，每条迁移边（含非法迁移）均有场景
- [ ] 每个功能点已对照 abnormal-checklist 检查，适用项均已生成场景或明确标注不适用原因
- [ ] 每个功能点已从安全、可靠性、性能三个视角审查（bug-category-checklists），适用项均已生成专项场景或标注不适用原因
- [ ] 有缓冲区/字符串处理的功能点，安全类已覆盖缓冲区边界精确值（长度-1/长度/长度+1）
- [ ] 有循环/查找/排序的功能点，性能类已覆盖最大规模输入与最坏情况构造
- [ ] 专项场景测试数据均为精确触发值，无「超长输入」类模糊描述
- [ ] 每个场景均可追溯到功能点编号，无来源不明场景
- [ ] 每条用例均已设计清理步骤：有持久化变更的用例有对应恢复操作，只读用例标注「无需清理」，无空缺
- [ ] demo 中体现的行为均有对应场景，且预期理解与 demo 一致
- [ ] 规格未定义而基于假设的场景已全部登记到「假设登记」章节

自检结果（各检查项通过情况、需求项/功能点/场景/用例数量、正常/异常分布、**四类 BUG 场景分布**）须体现在最终文档的「覆盖情况说明」章节。

### Step 5：生成测试设计文档（编写用例代码的直接依据）

按 `references/output-template.md` 的固定结构生成测试设计文档并**保存为文件**，此文档是下一阶段编写测试用例代码的直接参照物，必须先于代码完成。文档结构：概述 → 需求项对照表 → 功能点清单 → 测试场景矩阵 → 测试用例表 → 追溯矩阵 → 覆盖情况说明 → 假设登记。禁止增删章节或改变顺序（模板中的说明性文字应替换为实际内容）。

生成后自查文档完整性：测试用例表中每条 TC 均有具体测试数据与可判定的预期结果（无占位符、无「任意值」类表述）；若发现缺失，补全文档后才能进入 Step 6。

### Step 6：依据测试设计文档编写测试用例代码（最终交付）

**代码必须以 Step 5 生成的测试设计文档为唯一依据**：编写前重新读取已保存的文档，按文档中的用例逐条实现；不得凭记忆写代码，不得跳过文档直接从场景矩阵或规格实现。

**分批编写（硬性约束）**：待写用例总数超过 10 条时必须分批写入，禁止一次性生成全部用例：

1. **批次大小**：单批以 **8 条**为基准（区间 5-10）：含清理步骤、多断言点的复杂用例取下限 5；简单参数校验类用例可放宽到 10。总用例数 ≤10 条时可单批完成。
2. **分批方式**：按功能点分批，同一功能点的用例归入同一批，不得跨批拆散；单个功能点用例超过 10 条时，按用例编号顺序在其内部拆分。
3. **批内流程**：每批写入前对照文档确认本批用例的测试数据与预期结果 → 写入 → 完成本批核验（对照文档 + 语法）→ 通过后继续下一批；核验不通过先修复本批，不带问题进入下一批。批次之间连续执行，无需等待用户。
4. **每批为完整可编译单元**：本批的测试函数与注册代码在同批写入，保证任一批次写入后文件均可编译。

将新增测试用例写入 `testcase/testcase.c`：

1. 写入前必须先读取项目 `testcase/` 路径下既有的 testcase.c（若存在），确认已有内容、函数结构、断言方式与注册方式。
2. 新增用例**追加**写入，不删除、不修改已有用例与 demo 代码；若文件不存在，按 demo 结构新建。
3. 每条用例对应一个测试函数，函数名含用例编号（如 `tc_001_正常下单` 风格按 demo 命名习惯调整），保证代码与文档用例一一对应、可追溯。
4. 严格遵循 demo 提取的框架约定：断言宏、头文件、测试注册/运行入口、缩进与命名风格。
5. 测试数据、预期结果、用例数量以文档为准**原样落入代码**，不得增删改；文档中基于假设的用例同样实现（代码注释标注「基于假设 A-xx」）。
6. **清理步骤同步落码**：文档中每条用例的清理步骤必须在测试函数中实现——demo 框架提供 teardown/fixture 机制的优先使用该机制；否则在断言之后执行清理代码。若框架断言失败会中断函数导致清理被跳过，应改为「先记录断言结果 → 执行清理 → 最后统一判定」的模式，保证清理在用例失败时依然执行。「无需清理」的用例在函数末尾注释标注。
7. 全部批次完成后执行整体双重核验：**对照文档**——新增函数数量与文档用例数一致、逐条核对测试数据与预期结果无偏差、有清理步骤的用例代码中均有对应清理实现；**语法核验**——括号配对、分号、变量声明、已按 demo 方式注册到运行入口。

完成后向用户一次性交付 testcase.c 与测试设计文档，交付说明中注明 testcase.c 中新增用例的数量与对应的功能点范围。
