# Test Design（测试设计）

## Overview

此 skill 用于在**无人干预**条件下，将功能设计规格与测试样例 demo（位于项目 `testcase/` 路径下）自动转化为完整测试设计与测试用例代码，并以**发现 BUG**（而非仅验证功能正确）为导向：测试场景覆盖功能（正常/异常）以及安全、可靠性、性能三类 BUG 专项。核心做法：先把规格逐条编号拆解为需求项，再映射为可追溯的功能点清单，对每个功能点按确定性规则选用用例设计方法生成正常/异常测试场景，并逐功能点套用四类 BUG 专项清单生成对抗性场景，经覆盖率自检关卡后展开为详细用例，**先生成测试设计文档（作为编写用例的直接参照物），再依据该文档将新增测试用例按 demo 格式以 C 代码写入 `testcase/testcase.c`**。

**运行模式：全程自动，禁止中途向用户提问或等待确认。** 所有不确定信息由模型按「合理假设原则」自行处理并登记。

**输入前提：目标系统是黑盒**——本地不包含其源码，唯一的输入材料是**功能设计文档**与**测试样例 demo**（位于项目 `testcase/` 路径下），实现细节不可读，行为只能通过规格、demo 与黑盒运行观察来理解。

## 核心原则（防跑偏、防遗漏，全程必须遵守）

1. **只基于输入材料，禁止臆造需求**：所有测试场景必须来源于功能设计规格或 demo 的明确信息。规格未定义的行为，按合理假设设计并登记到「假设登记」章节，同时在场景中标注「基于假设」。
2. **BUG 发现导向的对抗性思维**：测试的目的不是证明功能正确，而是主动构造能暴露 BUG 的条件。功能场景（以需求为出发点）之外，每个功能点必须再从安全、可靠性、性能三个视角审查一遍（见 references/bug-category-checklists.md），安全类按「不应崩溃/不应越界」、可靠性类按「应报错而非崩溃」、性能类按「应在合理时间内返回」作为基线预期。
3. **宁多勿漏，且以判据收敛**：无法判断某项是否需要覆盖时，一律设计场景并标注。漏分析是本任务最大风险，多余场景的成本远低于遗漏场景的损失。**停止条件是可核对的判据（覆盖台账清零 + 审计轮完成），不是「想不出更多了」**；全部分析与审计轮必须在单次调用内完成，不得留待用户后续补充。
4. **先设计后编码，每步有中间产物**：中间产物链为 需求项清单 → 功能点清单 → 待验证问题清单 → 因子表 → 场景矩阵 → 用例表 → 测试设计文档 → testcase.c 用例代码 → 编译与运行验证结果。测试设计文档必须先于代码完成并作为编码的唯一依据；用例代码必须通过编译与运行验证才算完成。**设计文档完成前禁止向 `testcase/` 写入任何测试代码（含探针）**，设计阶段的行为验证只能走 Step 0「黑盒行为验证规则」。
5. **全程可追溯**：需求项（REQ-xx）→ 功能点（FP-xx）→ 场景（TS-xxx）→ 用例（TC-xxx）四级编号逐级映射，最终文档必须包含两级追溯矩阵，任何一级出现无来源或无覆盖的条目均视为分析遗漏。
6. **确定性方法路由**：按「方法路由表」为每个功能点选择设计方法，不得凭感觉自由发挥；所有功能点必须用异常场景清单（见 references/abnormal-checklist.md）和四类 BUG 专项清单兜底补充。
7. **关卡不通过则返工**：覆盖率自检关卡（Step 4）中的检查项必须逐条核对，任何一条不满足必须返回上一步补充，禁止带缺口输出。
8. **职责分工：主 agent 专注分析，非分析类工作一律委派**：
   - **主 agent 只做测试场景分析**——规格拆解、需求项编号、功能点提取、因子分析、单功能点场景设计、BUG 专项、输出域校验、穷尽性审计、用例设计、设计文档编写，以及**对子 agent 产出的整合与校验**。这些是决定交付质量的核心工作，不得被环境类事务打断。
   - **委派清单**：环境与工具类（构建方式、框架识别、格式提取、环境依赖、结果判定、报错排查）、黑盒行为验证、**跨功能点组合场景分析（由专职子 agent 承担，主 agent 提供功能点与因子表并整合结果）**。任务定义见 `references/subagent-tasks.md`。
   - **并发上限**：**任何时刻最多并行 2 个子 agent**；待其中任务完成后再按需派发新任务，禁止一次性铺开全部任务。
   - **主 agent 不接收过程产物**：编译日志、报错堆栈、试错轮次一律不进入主推理链；子 agent 只回传「结论 + 一行证据 + 可直接使用的小产物（命令序列/骨架代码/约定清单/场景表）」。
   - **修改 `testcase.c` 始终由主 agent 执行**，保证设计文档与代码的一致性由掌握设计全貌的一方控制。

## Workflow

### Step 0：输入材料解析

**派发说明**：本阶段的子 agent 任务（T1-T4）与探针验证（T5）按核心原则 8 的并发上限分批派发——**每批最多 2 个，当前批完成后再派下一批**。

**材料 1：功能设计规格**

逐段逐条通读，为每条可验证的陈述分配需求项编号（REQ-01、REQ-02…）。需求项包括但不限于：

- 明确的功能描述（动词句）
- 输入约束（类型、范围、格式、必填性）
- 输出与提示文案（每个错误提示即一条需求项）
- 业务规则、逻辑分支、计算公式
- 状态定义与流转
- 权限与角色规则
- **隐性需求**：规格中一笔带过但可验证的内容（如"默认值为 X""页面显示 Y"）

**材料 2：测试样例 demo（位于项目 `testcase/` 路径下）**

demo 的**格式约定提取**（测试框架与断言方式、函数结构与命名、注册/运行方式、代码风格）**委派子 agent 完成**（任务 T2、T3，见 `references/subagent-tasks.md`），主 agent 只接收「用例编写与运行约定清单 + 最小骨架代码」作为结论。主 agent 自身解析以下与设计直接相关的价值：

1. **隐含行为**：demo 中体现但规格未写明的行为（边界处理、异常提示、默认逻辑），作为隐含需求项补充进需求项清单，来源标注「demo 推断」。
2. **理解校准**：将 demo 样例代入自己的理解中验证，若与 demo 实际表现矛盾，说明理解有偏差，必须回头修正需求项清单。

写入 `testcase/testcase.c` 的新增用例必须严格遵循子 agent 提取的格式约定。若项目 `testcase/` 路径下不存在 demo，按规格继续，用例按标准 C 断言风格编写并登记假设。

**黑盒行为验证规则**

规格与 demo 仍留有行为歧义时按以下规则处理，**不得用探测代替设计**：

1. **需求来源优先级：规格 > demo > 黑盒观察**。三者冲突时以规格为准，冲突点登记「假设登记」；**黑盒观察只用于校准理解，不得直接作为预期结果的依据**（预期必须能从规格或 demo 推导）。
2. **待验证问题清单（主 agent 的中间产物）**：把行为歧义整理为 `问题编号（PQ-01…）| 待验证的行为假设 | 影响的 REQ/功能点`。每条须能用一次探针运行判定，不得笼统（如「××功能怎么工作」）。
3. **探针由子 agent 执行**（派发规则与输出契约见核心原则 8 及 `references/subagent-tasks.md` T5）：子 agent 通过目标系统对外接口（接口形态由 T1/T2 确认）在临时目录验证并只回传结论表；主 agent 将结论写回需求项清单（来源标注「黑盒验证」）或「假设登记」。探针不得扩展为成批的系统性测试——系统性覆盖只能由 Step 1-2 产出。
4. **禁止事项**：设计文档完成前不得向 `testcase/` 写入任何测试代码（含探针、试验性代码）；探针代码与过程产物不得出现在任何交付物中。

### Step 1：功能点提取（两遍扫描，防漏关键步骤）

**第一遍：正向提取**。将需求项归组为功能点，每个功能点包含：

| 字段 | 说明 |
|------|------|
| 编号 | FP-01、FP-02…（全文档唯一） |
| 功能点名称 | 动宾结构，如「提交订单」「校验手机号格式」 |
| 来源需求项 | REQ-xx 列表（至少 1 条，可多条归组） |
| 输入 | 输入项、类型、取值范围/格式约束 |
| 处理规则 | 规格/demo 中明确的业务规则、逻辑分支 |
| 输出/预期行为 | 成功与失败时的表现 |
| 前置条件 | 触发该功能点所需状态、权限、数据 |
| 特征标签 | 【输入域】【规则组合】【流程】【状态流转】【交互界面】等，用于 Step 2 方法路由 |

**第二遍：反向查漏（必须执行，不可跳过）**。重新通读规格全文，按以下维度逐项检查是否已全部纳入功能点清单：

- 每个输入字段 / 界面控件 / 接口参数
- 每个输出结果 / 每条提示文案
- 每条业务规则的每个分支
- 每个状态及其所有出入迁移
- 每种角色 / 权限组合
- 每个异常处理描述
- demo 中出现但规格正文未提及的行为

发现遗漏立即补入功能点清单。完成后输出「需求项对照表」（REQ → FP 映射），**任何 REQ 未被 FP 覆盖即视为分析遗漏，必须处理（归组或单独建 FP）后方可继续**。

### Step 2：测试场景分析（因子分析 → 单功能点场景 → 跨功能点组合场景 → 四类 BUG 专项场景 → 输出域校验 → 穷尽性审计）

对每个功能点，按「先枚举因子、再选方法、后反向校验」的顺序产出「测试场景矩阵」。方法详见 `references/design-methods.md`。

**子流程 2-0：测试因子分析（每个功能点必做，先于一切方法）**。按 design-methods.md 第 0 节，对每个功能点从五个维度枚举测试因子并给出取值水平：**输入因子**（每个输入参数至少一个因子，含隐藏参数与可选参数）、**状态因子**（前置/后置状态、全局与会话状态）、**时序因子**（顺序、次数、间隔、并发）、**数据因子**（规模、内容、分布）、**环境因子**（资源、依赖、配置）。完成后执行**三必查**：每个输入参数在因子表中、每个可达状态在状态因子中、每个输出（含全部错误码）能被某组因子触发。因子表是后续所有场景分析的统一素材——**没有因子表不得开始设计场景**。

**方法路由表（确定性规则，作用对象为因子表）**：

| 因子表特征 | 必选方法 |
|------------|----------|
| 有输入域因子（数值、文本长度、格式、日期等） | 等价类划分 + 边界值分析 |
| 存在多条件组合决定结果的规则 | 判定表法（条件多且有约束时用因果图辅助） |
| 有时序因子（跨步骤流程、顺序、重复调用） | 场景法（基本流 + 备选流），按场景法覆盖时序因子 |
| 有状态因子（对象有状态流转） | 状态迁移法（覆盖所有迁移边） |
| 有 ≥2 个输入因子 | 成对组合（pairwise）为默认最低组合强度；组合仍爆炸时用正交表精简 |
| 多个功能点存在状态/数据依赖 | 跨功能点组合场景法（见 design-methods.md 第 10 节） |
| 所有功能点（兜底） | 错误推测法，对照 `references/abnormal-checklist.md` 逐项检查 |
| 所有功能点（BUG 专项，必做） | 对照 `references/bug-category-checklists.md` 逐项检查 |
| 所有功能点（覆盖校验，必做） | 输出域分析法：每个输出/错误码必有场景触发 |

**子流程 2a：单功能点功能场景**。以因子表为素材，按方法路由表逐行套用生成正常/异常功能场景；单因子变化生成基本场景，多因子按判定表/成对组合/场景法规则组合。

**子流程 2b：跨功能点组合场景（委派专职子 agent，必做，不可跳过）**。规格分段描述的功能在实际业务中会串成有状态旅程，状态残留、撤销重做、中间态查询类 BUG 只有组合场景能暴露。本子流程**委派一个专职子 agent 专注做多功能点叠加分析**（任务 T8，见 `references/subagent-tasks.md`）：

1. **主 agent 准备并传递输入**：功能设计规格（或其相关章节）、需求项清单、功能点清单（含角色、前置条件、输出）、各功能点的因子表、数量下限与输出格式要求。
2. **子 agent 专责分析**：识别功能角色与依赖 → 构建全局状态机 → 三层发散生成（两步序列矩阵穷举、六模式多步旅程、组合 × 因子交叉）→ 自检数量下限 → **只回传组合场景表与统计**（不返回分析过程叙述）；详细方法见 design-methods.md 第 10 节。
3. **主 agent 整合与校验**：对返回场景统一编号、与单功能点场景查重、核对数量下限（矩阵适用项 100%、每个有状态交互对象 × 六模式各 ≥1 条、组合场景总数 ≥ 单功能点场景数的 1/3，不满足视为发散不足）及每条预期结果的推导依据；通过后纳入场景矩阵与覆盖台账（组合透镜）。**发现缺口时带具体缺口再次派发该子 agent 补充**。

**子流程 2c：四类 BUG 专项场景（必做，不可跳过）**。对每个功能点依次套用 `references/bug-category-checklists.md` 的安全、可靠性、性能三节清单，适用项各生成专项场景（功能类清单用于查漏补缺）。核心要求：以「怎么让它出错」为出发点构造精确攻击值，**测试数据必须是精确触发值**（如「256 字节输入」「INT_MAX」「循环 1000 次」），禁止「超长输入」类模糊描述。

**子流程 2d：输出域校验（必做）**。按 design-methods.md 第 9 节枚举每个功能点的全部输出（成功输出 + 每个错误码/提示 + 副作用），无场景触发的输出反推条件补场景；确实无法触发的登记「假设登记」并说明依据。

**子流程 2e：穷尽性审计（必做，收敛关卡）**。前四个子流程产出的矩阵只是初稿，此关卡把单次通读的必然遗漏补全。按 `references/exhaustive-audit.md` 执行五个动作：建立覆盖台账（七类义务，先列义务再设计）→ 六透镜逐轮扫描回填 → 隐藏场景猎取清单逐功能点比对 → 强制追加配额（每功能点 3 条 + 全局 10 条候选，逐条判定纳入/不适用）→ 至少一轮反向审计（重读规格原文比对）。

**收敛判据（全部满足才可进入 Step 3，且全部轮次在本次调用内完成）**：台账适用格全部回填、空单元格清零；反向审计完成；追加配额逐条判定完毕；数量下限满足（组合场景 ≥ 单功能点场景数 1/3、异常场景 ≥ 正常场景 50%）。

场景矩阵中每个场景必须包含：场景编号（TS-xxx）、对应功能点编号（组合场景记序列）、场景描述、类型（正常/异常）、**BUG 类别（功能/安全/可靠性/性能）**、使用的设计方法、预期结果（须来自规格或 demo；未定义的按合理假设或核心原则 2 的基线预期给出并标注「基于假设」）。四类 BUG 类别各有至少 1 个专项场景优先级不低于 P1。

### Step 3：用例展开

将每个测试场景展开为 1 条或多条可执行测试用例：

- **用例编号**：TC-xxx（与场景编号 TS-xxx 对应，可追溯）
- **用例标题**：一句话描述（动宾结构）
- **优先级**：P0（主流程正常场景）/ P1（重要分支与高频异常）/ P2（低概率异常与边界组合）
- **前置条件**：状态、数据、权限准备
- **测试数据**：具体到值（含边界值具体取值），不得写「任意合法值」
- **操作步骤**：编号步骤，单步骤单一操作
- **清理步骤**：用例执行后恢复到执行前状态的资源清理操作（见下方清理规则）
- **预期结果**：具体可判定，对应功能点的输出定义；demo 有格式约定的按 demo 格式表述

**清理步骤规则（每条用例必填）**：

1. 凡用例产生了持久化变更（新增/修改/删除了数据、成员、记录、文件、状态），必须设计对应清理步骤将其恢复（如「删除本用例新增的成员 xxx」），避免污染后续用例。
2. 确无资源变更的只读用例，清理步骤填「无需清理」，不得留空。
3. 清理步骤必须**幂等**：目标资源已不存在时清理不报错、不影响用例判定。
4. 预期结果的验证数据在清理前采集完毕，清理不参与断言。

规则：一个场景含多组测试数据时拆为多条用例；预期结果含多个验证点时逐条列出。本阶段产物是用例表（设计层），C 代码在 Step 6 依据测试设计文档编写。

### Step 4：覆盖率自检（硬性关卡，替代人工评审）

逐条核对以下清单，任何一条不满足即返回对应步骤补充，全部满足才能输出：

- [ ] 每条需求项（REQ-xx）已映射到功能点，对照表无空缺
- [ ] 每个功能点已产出因子表并通过三必查（输入参数 / 可达状态 / 输出均无遗漏因子）
- [ ] 每个输出（含每个错误码/提示/副作用）均有至少 1 个场景触发，或已登记「无法触发」的判断依据
- [ ] 有 ≥2 个输入因子的功能点已满足成对组合覆盖
- [ ] 跨功能点组合：已委派专职子 agent 完成多功能点叠加分析并经主 agent 整合校验——两步序列矩阵适用项 100% 覆盖（不适用项有原因标注）、每个有状态交互对象 × 六种模式各 ≥1 条、组合场景总数 ≥ 单功能点场景数的 1/3
- [ ] **穷尽性审计已完成**：覆盖台账七类义务适用格全部回填且空单元格清零、六透镜逐轮扫描执行、反向审计完成（重读规格比对）、强制追加配额逐条判定
- [ ] 每个功能点 ≥1 正常场景；每个有输入约束的字段 ≥1 无效等价类场景；每条业务规则分支（含判定表每一列）与每条状态迁移边（含非法迁移）均被覆盖
- [ ] 每个功能点已对照 abnormal-checklist 与 bug-category-checklists 逐项检查，适用项均已生成场景或明确标注不适用原因
- [ ] 有缓冲区/字符串处理的功能点安全类覆盖了精确边界值（长度-1/长度/长度+1）；有循环/查找/排序的功能点性能类覆盖了最大规模与最坏情况构造
- [ ] 专项场景测试数据均为精确触发值，无「超长输入」类模糊描述
- [ ] 每个场景均可追溯到功能点编号，无来源不明场景；demo 中体现的行为均有对应场景且预期理解一致
- [ ] 每条用例均已设计清理步骤（有持久化变更的有恢复操作，只读用例标注「无需清理」），无空缺
- [ ] 基于假设的场景已全部登记「假设登记」；覆盖台账与审计记录已写入「覆盖情况说明」

自检结果（各检查项通过情况、需求项/功能点/因子/场景/用例数量、正常/异常分布、**四类 BUG 场景分布**、**输出域覆盖统计（输出总数与已触发数）**）须体现在最终文档的「覆盖情况说明」章节。

### Step 5：生成测试设计文档（编写用例代码的直接依据）

按 `references/output-template.md` 的固定结构生成测试设计文档并**保存为文件**，此文档是下一阶段编写测试用例代码的直接参照物，必须先于代码完成。文档结构：概述 → 需求项对照表 → 功能点清单 → 测试场景矩阵 → 测试用例表 → 追溯矩阵 → 覆盖情况说明 → 假设登记。禁止增删章节或改变顺序（模板中的说明性文字应替换为实际内容）。

生成后自查文档完整性：测试用例表中每条 TC 均有具体测试数据与可判定的预期结果（无占位符、无「任意值」类表述）；若发现缺失，补全文档后才能进入 Step 6。

### Step 6：依据测试设计文档编写测试用例代码（最终交付）

**代码必须以 Step 5 生成的测试设计文档为唯一依据**：编写前重新读取已保存的文档，按文档中的用例逐条实现；不得凭记忆写代码，不得跳过文档直接从场景矩阵或规格实现。

**分批编写（硬性约束）**：待写用例总数超过 10 条时必须分批写入，禁止一次性生成全部用例：

1. **批次大小**：单批以 **8 条**为基准（区间 5-10）：含清理步骤、多断言点的复杂用例取下限 5；简单参数校验类用例可放宽到 10。总用例数 ≤10 条时可单批完成。
2. **分批方式**：按功能点分批，同一功能点的用例归入同一批，不得跨批拆散；单个功能点用例超过 10 条时，按用例编号顺序在其内部拆分。
3. **批内流程**：每批写入前对照文档确认本批用例的测试数据与预期结果 → 写入 → 完成本批核验（对照文档 + 编译验证，编译命令见 Step 7）→ 通过后继续下一批；核验不通过先修复本批，不带问题进入下一批。批次之间连续执行，无需等待用户。
4. **每批为完整可编译单元**：本批的测试函数与注册代码在同批写入，保证任一批次写入后文件均可编译。

将新增测试用例写入 `testcase/testcase.c`：

1. 写入前必须先读取项目 `testcase/` 路径下既有的 testcase.c（若存在），确认已有内容、函数结构、断言方式与注册方式。
2. 新增用例**追加**写入，不删除、不修改已有用例与 demo 代码；若文件不存在，按 demo 结构新建。
3. 每条用例对应一个测试函数，函数名含用例编号（如 `tc_001_正常下单` 风格按 demo 命名习惯调整），保证代码与文档用例一一对应、可追溯。
4. 严格遵循 demo 提取的框架约定：断言宏、头文件、测试注册/运行入口、缩进与命名风格。
5. 测试数据、预期结果、用例数量以文档为准**原样落入代码**，不得增删改；文档中基于假设的用例同样实现（代码注释标注「基于假设 A-xx」）。
6. **清理步骤同步落码**：文档中每条用例的清理步骤必须在测试函数中实现——demo 框架提供 teardown/fixture 机制的优先使用该机制；否则在断言之后执行清理代码。若框架断言失败会中断函数导致清理被跳过，应改为「先记录断言结果 → 执行清理 → 最后统一判定」的模式，保证清理在用例失败时依然执行。「无需清理」的用例在函数末尾注释标注。
7. 全部批次完成后执行整体双重核验：**对照文档**——新增函数数量与文档用例数一致、逐条核对测试数据与预期结果无偏差、有清理步骤的用例代码中均有对应清理实现、**每个新增函数均能追溯到设计文档中的用例（无探针/试验性代码残留）**；**语法核验**——括号配对、分号、变量声明、已按 demo 方式注册到运行入口。

核验通过后进入 Step 7 编译与运行验证。

### Step 7：编译与运行验证（交付前最后关卡）

编译与运行命令、可执行文件路径、结果判定方式**采用 Step 0 阶段子 agent 的确认结论**（任务 T1、T2、T6），直接执行，不再自行试探。参考命令（实际以子 agent 确认结果为准）：

```bash
cmake -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug -S . -B cmake-build-debug
cmake --build cmake-build-debug --config Debug --target all
./cmake-build-debug/main_test.exe
```

编译成功后生成可执行文件 `main_test.exe`；若目标环境非 Windows/无 MinGW，去掉 `-G "MinGW Makefiles"` 参数使用默认生成器，可执行文件名以实际生成结果为准。

**编译失败处理**：派发排查任务（T7）给子 agent，返回「根因 + 涉及位置 + 修复方案 + 是否为新增代码问题」；主 agent 依据方案修复 testcase.c 中的新增代码（修复仅限新增代码，不得改动既有用例与 demo 代码），重新编译直至通过。**主 agent 不接收编译日志全文**。编译不通过禁止交付。

**运行验证（本地无 BUG 系统上执行，全部用例必须通过）**：基于**没有 BUG 的正确系统**，验证标准为：**所有新增用例必须全部通过**。运行验证的作用是校准用例自身的正确性——本地跑不过，说明用例的预期理解或实现有偏差。处理规则：

1. **任何失败均为用例自身缺陷**（断言失败、崩溃中断、超时均算）：核对测试数据与预期结果是否与规格/demo 一致、断言写法是否正确、清理逻辑是否误判，修正用例后重新编译运行，直至全部通过。禁止为了让用例通过而偏离规格修改预期；若失败源于对规格理解的偏差，修正用例预期并同步更新测试设计文档（含「假设登记」中的对应记录）。失败根因不明确时派发 T7 定位。
2. **崩溃即缺陷**：正确系统应对异常输入优雅处理，预期「不应崩溃」的安全/可靠性用例在本地不应真的崩溃；若个别用例导致运行器中断，该用例必然存在预期或写法错误，修复后重跑。
3. **用例独立性验证**：全部通过后，完整再运行一次，确认无因前序用例残留数据导致的偶发失败；若有，核查对应用例的清理实现。

全部用例通过（且复跑稳定）才算验证完成，进入交付。

完成后向用户一次性交付 testcase.c 与测试设计文档，交付说明中注明：新增用例数量与对应的功能点范围、编译结果、运行验证结果（全部通过）。
