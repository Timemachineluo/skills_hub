# Test Design（测试设计）

## Overview

此 skill 用于在**无人干预**条件下，将功能设计规格（及测试样例 demo）自动转化为完整的测试设计文档与测试用例。核心做法：先把规格逐条编号拆解为需求项，再映射为可追溯的功能点清单，对每个功能点按确定性规则选用用例设计方法生成正常/异常测试场景，经覆盖率自检关卡后展开为详细用例，最终按固定模板输出 Markdown 文档。

**运行模式：全程自动，禁止中途向用户提问或等待确认。** 所有不确定信息由模型按「合理假设原则」自行处理并登记。

## 核心原则（防跑偏、防遗漏，全程必须遵守）

1. **只基于输入材料，禁止臆造需求**：所有测试场景必须来源于功能设计规格或 demo 的明确信息。规格未定义的行为，按合理假设设计并登记到「假设登记」章节，同时在场景中标注「基于假设」。
2. **宁多勿漏**：无法判断某项是否需要覆盖时，一律设计场景并标注。漏分析是本任务最大风险，多余场景的成本远低于遗漏场景的损失。
3. **每一步有中间产物**：工作流分六个阶段，每阶段必须产出确定的中间产物（需求项清单 → 功能点清单 → 场景矩阵 → 用例表 → 最终文档）。禁止跳过中间产物直接写最终文档。
4. **全程可追溯**：需求项（REQ-xx）→ 功能点（FP-xx）→ 场景（TS-xxx）→ 用例（TC-xxx）四级编号逐级映射，最终文档必须包含两级追溯矩阵，任何一级出现无来源或无覆盖的条目均视为分析遗漏。
5. **确定性方法路由**：按「方法路由表」为每个功能点选择设计方法，不得凭感觉自由发挥；所有功能点必须用异常场景清单（见 references/abnormal-checklist.md）兜底补充。
6. **关卡不通过则返工**：覆盖率自检关卡（Step 4）中的检查项必须逐条核对，任何一条不满足必须返回上一步补充，禁止带缺口输出。

## Workflow

### Step 0：输入材料解析

**材料 1：功能设计规格**

逐段逐条通读，为每条可验证的陈述分配需求项编号（REQ-01、REQ-02…）。需求项包括但不限于：

- 明确的功能描述（动词句）
- 输入约束（类型、范围、格式、必填性）
- 输出与提示文案（每个错误提示即一条需求项）
- 业务规则、逻辑分支、计算公式
- 状态定义与流转
- 权限与角色规则
- **隐性需求**：规格中一笔带过但可验证的内容（如"默认值为 X""页面显示 Y"）

**材料 2：测试样例 demo**

解析 demo 的三重价值：

1. **格式规范**：提取用例的输入格式、输出格式、断言方式等编写约定，最终用例必须遵循该格式。
2. **隐含行为**：demo 中体现但规格未写明的行为（边界处理、异常提示、默认逻辑），作为隐含需求项补充进需求项清单，来源标注「demo 推断」。
3. **理解校准**：将 demo 样例代入自己的理解中验证，若与 demo 实际表现矛盾，说明理解有偏差，必须回头修正需求项清单。

若用户只提供规格未提供 demo，按规格继续，用例格式按本 skill 默认模板处理。

### Step 1：功能点提取（两遍扫描，防漏关键步骤）

**第一遍：正向提取**。将需求项归组为功能点，每个功能点包含：

| 字段 | 说明 |
|------|------|
| 编号 | FP-01、FP-02…（全文档唯一） |
| 功能点名称 | 动宾结构，如「提交订单」「校验手机号格式」 |
| 来源需求项 | REQ-xx 列表（至少 1 条，可多条归组） |
| 输入 | 输入项、类型、取值范围/格式约束 |
| 处理规则 | 规格/demo 中明确的业务规则、逻辑分支 |
| 输出/预期行为 | 成功与失败时的表现 |
| 前置条件 | 触发该功能点所需状态、权限、数据 |
| 特征标签 | 【输入域】【规则组合】【流程】【状态流转】【交互界面】等，用于 Step 2 方法路由 |

**第二遍：反向查漏（必须执行，不可跳过）**。重新通读规格全文，按以下维度逐项检查是否已全部纳入功能点清单：

- 每个输入字段 / 界面控件 / 接口参数
- 每个输出结果 / 每条提示文案
- 每条业务规则的每个分支
- 每个状态及其所有出入迁移
- 每种角色 / 权限组合
- 每个异常处理描述
- demo 中出现但规格正文未提及的行为

发现遗漏立即补入功能点清单。完成后输出「需求项对照表」（REQ → FP 映射），**任何 REQ 未被 FP 覆盖即视为分析遗漏，必须处理（归组或单独建 FP）后方可继续**。

### Step 2：测试场景分析

对每个功能点，按方法路由表选择设计方法，产出「测试场景矩阵」。方法详见 `references/design-methods.md`。

**方法路由表（确定性规则）**：

| 功能点特征 | 必选方法 |
|------------|----------|
| 有输入域（数值、文本长度、格式、日期等） | 等价类划分 + 边界值分析 |
| 存在多条件组合决定结果的规则 | 判定表法（条件多且有约束时用因果图辅助） |
| 涉及跨步骤业务流程 | 场景法（基本流 + 备选流） |
| 对象有状态流转（如订单状态） | 状态迁移法（覆盖所有迁移边） |
| 多参数组合且组合爆炸 | 正交实验法 |
| 所有功能点（兜底） | 错误推测法，对照 `references/abnormal-checklist.md` 逐项检查 |

场景矩阵中每个场景必须包含：场景编号（TS-xxx）、对应功能点编号、场景描述、类型（正常/异常）、使用的设计方法、预期结果（须来自规格或 demo；两者均未定义的按合理假设给出并标注「基于假设」）。

正常场景与异常场景用类型列区分。异常场景数量不得少于正常场景的 50%（若低于，说明异常分析不足，回到路由表补做）。

### Step 3：用例展开

将每个测试场景展开为 1 条或多条可执行测试用例：

- **用例编号**：TC-xxx（与场景编号 TS-xxx 对应，可追溯）
- **用例标题**：一句话描述（动宾结构）
- **优先级**：P0（主流程正常场景）/ P1（重要分支与高频异常）/ P2（低概率异常与边界组合）
- **前置条件**：状态、数据、权限准备
- **测试数据**：具体到值（含边界值具体取值），不得写「任意合法值」
- **操作步骤**：编号步骤，单步骤单一操作
- **预期结果**：具体可判定，对应功能点的输出定义；demo 有格式约定的按 demo 格式表述

规则：一个场景含多组测试数据时拆为多条用例；预期结果含多个验证点时逐条列出；用例格式若比赛有明确要求（从 demo 提取），以比赛格式为准。

### Step 4：覆盖率自检（硬性关卡，替代人工评审）

逐条核对以下清单，任何一条不满足即返回对应步骤补充，全部满足才能输出：

- [ ] 每条需求项（REQ-xx）已映射到功能点，需求项对照表无空缺
- [ ] 每个功能点至少有 1 个正常场景
- [ ] 每个有输入约束的字段至少有 1 个无效等价类场景
- [ ] 每条业务规则的每个分支（含判定表每一列）至少被 1 个场景覆盖
- [ ] 有状态流转的功能点，每条迁移边（含非法迁移）均有场景
- [ ] 每个功能点已对照 abnormal-checklist 检查，适用项均已生成场景或明确标注不适用原因
- [ ] 每个场景均可追溯到功能点编号，无来源不明场景
- [ ] demo 中体现的行为均有对应场景，且预期理解与 demo 一致
- [ ] 规格未定义而基于假设的场景已全部登记到「假设登记」章节

自检结果（各检查项通过情况、需求项/功能点/场景/用例数量、正常/异常分布）须体现在最终文档的「覆盖情况说明」章节。

### Step 5：生成测试设计文档

按 `references/output-template.md` 的固定结构生成 Markdown 测试设计文档并保存为文件，向用户一次性交付。文档结构：概述 → 需求项对照表 → 功能点清单 → 测试场景矩阵 → 测试用例表 → 追溯矩阵 → 覆盖情况说明 → 假设登记。禁止增删章节或改变顺序（模板中的说明性文字应替换为实际内容）。
